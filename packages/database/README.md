# @noivos/database

Schema and RLS policies for the Noivos Postgres database, hosted on **Neon** (see `PROJECT_MEMORY.md` §6.4 for the Supabase → Neon pivot and why this looks different from `docs/04 Database/Database Architecture.md`'s original Supabase-authored version).

## What's here

- `migrations/0001_init.sql` — full schema: identity/Partnership, financial accounts and transactions, budgets and goals, Wedding Mode, AI conversations, engagement (Money Meetings, activity feed, notifications, challenges), billing, attachments.
- `migrations/0002_rls.sql` — Row-Level Security policies, the actual privacy enforcement layer (Database Architecture §1/§10). Every policy reads a `current_user_id()` helper backed by a Postgres session variable, **not** Supabase's `auth.uid()`.
- `migrations/0003_add_birthdate.sql` — adds `users.birthdate`, not in the original Database Architecture doc; added for `apps/web`'s locked Name & Birthdate identity-verification setting.
- `migrations/0004_tighten_goal_contributions_rls.sql` — closes a real gap in `goal_contributions_write`: it only checked the inserting user named themselves as contributor, never that the goal itself was theirs to write to.
- `migrations/0005_add_activity_feed_insert_policy.sql` — adds the INSERT policy `activity_feed_events` never had; without it, no per-user connection can write an activity event at all (see `PROJECT_MEMORY.md` §6.0's no-service-role-for-live-requests rule).
- `migrations/0006_add_partnership_invite_accept_flow.sql` — adds the two `partnership_invites` RLS policies a real accept-invite flow needs: any pending invite is selectable (the invite_token itself is the secret), and any signed-in user can transition a pending invite to accepted/declined. Without these, only the inviter could ever read or update an invite row — there was no way for the actual invitee to join.
- `migrations/0007_close_rls_audit_gaps.sql` — closes six gaps found by a systematic audit (every table cross-referenced against every policy): `plaid_items` and `account_balance_snapshots` had **no RLS enabled at all**; `challenges` (the catalog table) also had none; `attachments`, `ai_messages`, and `challenge_participations` each had a SELECT policy but no INSERT policy. None were exploitable yet (nothing in the app queries these tables), but each would be a real hole the moment Plaid, receipts, AI Coach messages, or Challenges get built.
- `migrations/0008_fix_bootstrap_race_conditions.sql` — adds five unique indexes (three of them partial, since a plain multi-column `unique` doesn't dedupe when a column is `null`) closing five check-then-insert race conditions found via a static schema read: `money_meetings`, `budgets`, `categories`, `budget_categories`, and `accounts` (the one-manual-account-per-user case) could all end up with duplicate rows if two requests raced the same "does this exist yet?" check — most realistically both partners loading Budget or Home at the same moment. `wedding_details` already had this right from `0001_init.sql`; these five never got the matching treatment.
- `migrations/0009_fix_categories_write_rls.sql` — fixes `categories_write`, the only write policy in `0002_rls.sql` shaped with `OR` instead of `AND` and missing a `was_partnership_member()` check on its partnership branch. Since shared categories are created with `owner_id = null`, this meant write access to **any** Partnership's shared categories rested entirely on "is some partnership active" — true for any signed-in user, not just members of that Partnership. Not reachable through the app's current UI, but a real hole at the actual enforcement layer.
- `migrations/0010_fix_with_check_membership_gaps.sql` — a second instance of the same bug class as `0009`, found by extending that correctness read across the rest of `0002_rls.sql`: `wedding_vendors_all`, `wedding_family_contributions_all`, `wedding_checklist_items_all`, and `money_meetings_all` each had a correct `USING` clause but a `WITH CHECK` clause missing the same `was_partnership_member()` check, meaning `WITH CHECK` (the only clause governing INSERT) let any authenticated user insert a row falsely attributed to a Partnership they were never a member of.
- `migrations/0011_add_foreign_key_indexes.sql` — adds plain btree indexes on foreign-key columns that RLS policies and application queries actually filter/join on. Postgres doesn't auto-index FK columns the way it does primary keys; until this, the only indexes in the whole schema were the hand-added uniqueness constraints from `0001`/`0008`. Most notably, `was_partnership_member()` — the single most-called RLS helper function, referenced by nearly every policy in the schema — had zero index support for its own `partnership_members` lookup.
- `migrations/0012_fix_write_policy_membership_gaps.sql` — fixes a severe cross-tenant data-injection hole in `accounts_write`, `transactions_write`, `recurring_expenses_write`, `budgets_write`, and `goals_write`: all five checked `owner_id = current_user_id() and partnership_is_active(partnership_id)` but never `was_partnership_member(partnership_id)`, so any authenticated user could insert a row attributed to (and visible to the real members of) any other active Partnership. The same bug class as `0009`/`0010`, missed on those tables during that earlier audit.
- `migrations/0013_fix_activity_feed_insert_membership_gap.sql` — the same gap again, found by grepping every migration for `partnership_is_active()` rather than trusting `0012`'s own list was complete: `activity_feed_events_insert` (from `0005`, not `0002`, which is why the earlier sweeps missed it) had the identical shape. Lower severity — can only inject a misleading feed sentence, not real financial data — but the same real hole at the enforcement layer.

## The auth handoff (read before touching this)

Supabase gave RLS policies a free, built-in `auth.uid()`. Clerk (the new auth provider, per §6.4) is external to Postgres, so there's no equivalent for free. Instead:

1. Clerk authenticates the request and gives the API layer a `clerk_user_id`.
2. Before running **any** query on behalf of that user, the API layer's DB client must run, inside the same transaction:
   ```sql
   select set_config('app.current_user_id', $1, true); -- true = transaction-scoped
   ```
3. Every RLS policy in `0002_rls.sql` reads that value back via `current_user_id()`. If a query runs without setting it first, RLS correctly denies everything — that's a safety property, not a bug to work around.

**Never** connect with a superuser/bypass-RLS role for a live user request — reserved only for async/system-initiated writes (Plaid webhooks, scheduled jobs) per the hard rule in `PROJECT_MEMORY.md` §6.0 and Backend Architecture §2, and even those must replicate the ownership/sharing checks in code since RLS won't be doing it for them.

**Partnership accept-invite (2026-08-05) — the real second-person-joins flow, and a second migration this round.** Since 2026-08-03, inviting created a real solo Partnership + a pending invite row, but nothing let a second person actually join — `partnership_invites`' original RLS (0002_rls.sql) only let the *inviter* select/update their own invite. `0006_add_partnership_invite_accept_flow.sql` adds the two policies an invitee needs: read a pending invite (by its unguessable `invite_token`, the actual secret), and transition it to accepted/declined. Migration 0006 is now applied (2026-08-05); the real signed-in preview/accept round trip still needs a pass on the live Vercel deployment.

**Bootstrap race conditions (2026-08-07) — found via a static schema read, no live-database reproduction possible from this sandbox.** Five places in the app follow a "select, and if nothing's found, insert" shape with nothing preventing two concurrent requests from both passing the check and both inserting: `GET /api/money-meeting` (a duplicate `money_meetings` row for the same Partnership+week), `GET /api/budget`'s default-category bootstrap (duplicate `categories` rows — the most likely to actually trigger, since it runs on every first-ever Budget load and both partners loading Budget at once is a completely normal scenario), the same route's shared/personal budget-row creation (duplicate `budgets` rows), the same route's `budget_categories` seeding loop, and `findOrCreateManualAccount` in `lib/budget.ts` (duplicate "Manual Entries" `accounts` rows, fragmenting a user's own logged expenses across two accounts). `wedding_details` already had this handled correctly since `0001_init.sql` (a real `unique` column + `ON CONFLICT (partnership_id) DO NOTHING` in `POST /api/wedding`) — these five just never got the same treatment. `0008_fix_bootstrap_race_conditions.sql` adds the five unique indexes (three partial, since Postgres doesn't dedupe across `null` in a plain multi-column `unique` constraint — the personal/shared split on `budgets` and `categories` needed that); all five call sites now use `ON CONFLICT ... DO NOTHING` plus a fallback select for the ones that need the winning row's id back (`money_meetings`, `budgets`, `accounts`) — the two seeding loops (`categories`, `budget_categories`) don't need a fallback since a later `select` in the same request re-reads everything fresh regardless of who won. Verified: `tsc --noEmit` clean, a clean production build, and all 33 tests passing (one new: `findOrCreateManualAccount`'s race-loss fallback path, mocked). Migration applied 2026-08-07 — confirms the five partial-index definitions and every `ON CONFLICT` clause's match against them were syntactically correct against real Neon Postgres, which this sandbox couldn't verify on its own (no raw-TCP DB access).

**`categories_write` RLS bug (2026-08-07) — found via a correctness read of every write policy in `0002_rls.sql`, not a coverage check (coverage was already fully audited by `0007`).** Comparing every `for all`/write policy's logical shape against its siblings turned up one outlier: `accounts_write`, `transactions_write`, `recurring_expenses_write`, `budgets_write`, and `goals_write` all correctly `AND` an ownership/membership check with an active-partnership check. `categories_write` alone used `OR`, and its partnership branch called `partnership_is_active(partnership_id)` but never `was_partnership_member(partnership_id)` — it checked that *some* partnership was active, not that the current user actually belonged to it. Tracing `apps/web/src/app/api/budget/route.ts`'s category-bootstrap code confirmed shared categories are inserted with `owner_id = null` (unlike `budgets`, which stays owner-scoped even when shared), so the `owner_id = current_user_id()` branch is never true for a shared category — meaning write access to **every** shared category on the platform rested entirely on "is some Partnership active," true for any authenticated user regardless of membership. Not currently reachable through the app's own UI (no route lets a client supply an arbitrary `categoryId` for UPDATE/DELETE yet, and the one write path — the bootstrap insert — already succeeds cleanly per migration 0008's unique indexes), but this is the actual database-level privacy boundary this project treats as authoritative, not application code — same posture as `0007`'s audit, which enabled RLS on tables with zero current app usage rather than waiting for a route to reach them. `0009_fix_categories_write_rls.sql` drops and recreates `categories_write` with `AND` (matching every sibling policy) and the missing `was_partnership_member()` check added to both `using` and `with check`. The change only *adds* a required condition, so it can only narrow access, never grant anything the old policy didn't already (incorrectly) allow — it cannot break the one legitimate write path. No application-code change was needed (pure SQL/RLS), so there's nothing for `tsc`/tests/build to check beyond confirming the rest of the app still passes unaffected; `tsc --noEmit` run clean regardless. Applied 2026-08-07 — confirms the `AND`-shaped policy and the `was_partnership_member()` reference compiled and installed cleanly against real Neon Postgres. **All nine migrations are now live in the real database.**

**`WITH CHECK` membership gaps (2026-08-07) — a second instance of the same bug class, found by extending the `0009` correctness read across the rest of `0002_rls.sql`'s `for all` policies instead of stopping at the one table that pass happened to start with.** Four policies — `wedding_vendors_all`, `wedding_family_contributions_all`, `wedding_checklist_items_all`, `money_meetings_all` — have a `USING` clause that correctly requires `was_partnership_member()`, but a `WITH CHECK` clause that only requires `partnership_is_active()`, never membership. Since there's no `USING` clause at all on `INSERT` (no existing row to filter), `WITH CHECK` governs inserts entirely on these four tables — meaning any authenticated user, given (or guessing) another Partnership's `wedding_details_id`/`partnership_id` (a UUID, not secret), could insert a row falsely attributed to a Partnership they were never a member of, as long as it's active. The same gap also lets a genuine member of their own Partnership re-point an existing row's `wedding_details_id`/`partnership_id` at a *different* active Partnership via `UPDATE`, since the post-update check never re-verifies membership either. `wedding_details_write` (same file) already had the correct symmetric shape — `using (...active... and ...member...)` / `with check (...active... and ...member...)` — the pattern these four should have matched from the start. Not reachable through the app's current UI (every real write route derives the partnership/wedding_details id from the *writing user's own* active membership server-side), but this is the actual database-level enforcement layer, so fixed for the same reason `0009` was rather than left open. `0010_fix_with_check_membership_gaps.sql` adds the missing `was_partnership_member()` check to each `WITH CHECK` clause — narrows-only, can't break any of the four real write paths (`POST /api/wedding/vendors`, `.../family-contributions`, `.../checklist`, `GET /api/money-meeting`'s auto-create, `POST /api/money-meeting/complete`), all of which already supply an id the writing user genuinely belongs to. Also re-verified every remaining `for insert`/`for update` policy across `0002`, `0004`–`0007` for the same class of gap — all correctly scope to `current_user_id()`/`contributor_id`/`owner_id`/`initiated_by` or an `exists`-based membership check; `partnership_invites_select_pending`'s broad `status = 'pending'` visibility is a deliberate, already-documented design (the unguessable `invite_token` is the real secret, same trust model as most invite-link products), not a gap. No application-code change needed (pure SQL/RLS); `tsc --noEmit` run clean regardless. Applied 2026-08-07 — confirms all four `WITH CHECK` clauses compiled and installed cleanly against real Neon Postgres. **All ten migrations are now live in the real database.**

**Missing foreign-key indexes (2026-08-07) — found after the RLS correctness read went exhaustive with no further gaps (every SELECT/INSERT/UPDATE/ALL policy across all ten migrations checked), so this pass moved from correctness to performance instead of re-treading the same ground.** Reading `0001_init.sql`/`0008`'s `create unique index` statements end to end turned up a real gap that has nothing to do with correctness: Postgres does not automatically index foreign-key columns the way it does primary keys, and outside the handful of uniqueness constraints added for other reasons, **no table in this schema has ever had a plain lookup index**. Worst example: `was_partnership_member(p_partnership_id)` — `0002_rls.sql`'s single most-referenced helper function, called by nearly every RLS policy in the schema (accounts, transactions, categories, budgets, goals, every wedding table, money_meetings, activity_feed_events) — runs `where partnership_id = $1 and user_id = current_user_id()` against `partnership_members` with zero index support; every row-level access check across the whole app has been a sequential scan of that table since `0001_init.sql` shipped. Invisible at today's near-zero data volume, but this stops being invisible the moment either partner has a real transaction/goal/budget history — and by then it's a production incident, not a migration. Scoped `0011_add_foreign_key_indexes.sql` to tables the app actually queries today (confirmed by grepping every table name across `apps/web/src/app`/`lib` — 19 hits: `partnership_members`, `partnership_invites`, `accounts`, `categories`, `transactions`, `budgets`, `goals`, `goal_contributions`, `wedding_vendors`, `wedding_family_contributions`, `wedding_checklist_items`, `activity_feed_events`), and deliberately deferred the tables with zero current query traffic (`recurring_expenses`, `ai_conversations`/`ai_messages`/`ai_insights`, `notifications`, `challenges`/`challenge_participations`, `subscriptions`, `attachments`, `plaid_items`, `account_balance_snapshots` — the same set `0007` already flagged as unwired-to-any-route) rather than speculatively indexing tables no query touches yet. Also deliberately left `transactions.account_id` unindexed even though every other FK on that table got one — nothing (RLS or application code) currently filters or joins on it; noted in the migration itself so it isn't a silent gap when a per-account transaction view eventually ships. Purely additive (new indexes only, no policy/schema changes), so it can't change what any query returns, only how fast — plain `create index`, not `concurrently`, since this app has no production traffic yet and `concurrently` can't run inside the single-paste SQL Editor transaction every migration this session has used. A first attempt on 2026-08-08 failed (the founder pasted the filenames into the SQL Editor, not the file contents — Postgres errored on `0011_add_foreign_key_indexes` as trailing junk after a numeric literal); applied successfully on the second attempt the same day, once the actual SQL was pasted directly in chat.

**A severe write-policy membership gap, found while building the real Goals Personal/Shared toggle (2026-08-08).** Before wiring up the feature (which needed `POST /api/goals` to start actually setting `partnership_id`/`is_shared` on insert), re-checked that write path's real enforcement — and found `goals_write` had the exact same bug class already fixed twice this session (`0009`'s `categories_write`, `0010`'s four `WITH CHECK`-only gaps), just missed on this table (and four siblings) during `0010`'s own re-audit, which had incorrectly asserted the remaining policies "correctly scope to `current_user_id()`." `accounts_write`, `transactions_write`, `recurring_expenses_write`, `budgets_write`, and `goals_write` all shared the identical shape: `owner_id = current_user_id() and (partnership_id is null or partnership_is_active(partnership_id))` — checking that the row is owned by the writer and that the *referenced* Partnership is merely active, never that the writer is actually a *member* of it. Concretely: any authenticated user could `INSERT` a row with `owner_id = themselves` and `partnership_id` set to **any other active Partnership's id** (a UUID, not secret), and it would pass `WITH CHECK` — then, once `is_shared = true`, that table's own SELECT policy (correctly checking `was_partnership_member()` against the row's real `partnership_id`) would let every genuine member of that *other* Partnership see the attacker's injected row. A real cross-tenant data-injection hole across the five most sensitive financial tables in the schema — worse than `0009`'s, which only touched `categories`. Not reachable through the app's current UI (every real route derives `partnership_id` server-side from the writing user's own genuine membership), but the actual enforcement layer, so fixed now per this project's own stated philosophy (Database Architecture §1/§10). `0012_fix_write_policy_membership_gaps.sql` adds the missing `was_partnership_member(partnership_id)` check alongside `partnership_is_active(partnership_id)` in both `using` and `with check` on all five policies — narrows-only, can't break any real write path. Applied 2026-08-08.

**One more of the same, found by not trusting the previous entry's "complete" claim (2026-08-08).** After `0012`, grepped every migration file for `partnership_is_active(` rather than relying on memory of what had already been checked — since `0010`'s own re-audit had already once wrongly claimed completeness. Turned up `activity_feed_events_insert` (`0005_add_activity_feed_insert_policy.sql` — not part of `0002_rls.sql`'s original block, which is likely why every prior sweep of "the write policies" missed it): `with check (actor_id = current_user_id() and partnership_is_active(partnership_id))`, the identical missing-membership shape. Lower severity than `0012`'s five tables — `lib/activity.ts`'s `describeActivityEvent()` only ever renders a fixed set of known `event_type` templates, so an injected row can only produce a misleading *sentence* in someone's feed, not fabricated financial data — but the same real hole at the enforcement layer regardless of severity tier. `0013_fix_activity_feed_insert_membership_gap.sql` adds the missing check, narrows-only, matches `logActivityEvent()`'s own call sites exactly (always passes a `partnershipId` the calling user is already a genuine member of). Applied 2026-08-08. **All thirteen migrations are now live in the real database.**
